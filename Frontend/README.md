# Outdoor Adventures — Frontend (Rentals UI & Backend API Contract)

## 1. Local Setup & Environment Config

```bash
cd Frontend
npm install
npm run dev
```

### API Proxy Configuration (`next.config.ts` & `.env.example`)
- [`Frontend/next.config.ts`](./next.config.ts) automatically proxies `/api/:path*` to `process.env.NEXT_PUBLIC_API_BASE_URL || 'http://localhost:3001'`.
- By default, no `.env.local` is required if your Backend server runs on `http://localhost:3001`.
- To point to a different Backend port or URL, copy [`.env.example`](./.env.example) to `.env.local`:
  ```env
  NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
  ```

## 1.1 Pages

| URL | Who | What |
|-----|-----|------|
| `/` | Everyone | Home screen: choose **Reservations** or **Staff** |
| `/rentals` | Students, faculty, staff | Sign in with B# and reserve gear (roles: student / faculty / staff) |
| `/staff` | OAP staff | Sign in with your own username + password → OAP Reservations, Gear & Logistics, Reserve Gear, Users |

### Staff portal sign-in
- Each OAP staff member has **their own account**: a username plus a password generated by the system (`staff_accounts` table). There is no shared password and no "who's working" picker.
- The account's username is sent as `staffId` with every action, so check-outs, check-ins, and cleaning are recorded under the person who did them.
- The login lasts until the browser is closed. Deactivating an account or resetting its password signs it out right away.

**Tabs** (second row under the header): OAP Reservations · Gear & Logistics · Reserve Gear · Users · Dashboard · Categories · Reports.

Gear & Logistics, Dashboard, Categories, and Reports use sample data in [`InventoryPanel.tsx`](./app/staff/InventoryPanel.tsx). Edits carry between those tabs until sign-out or reload. Use Reserve Gear to create reservations.

**Users tab** has two clearly separate lists:
- **OAP staff accounts**: create an account (choose a username → the password is shown once to copy), reset someone's password, deactivate/reactivate.
- **Renters**: students, faculty, and staff who reserve gear (`users` table). Search, deactivate/reactivate.

**First account / locked out:** `cd Backend && npm run create-staff -- <username>` creates an account and prints its password once. Add `--reset` to give an existing account a new password.

### Staff API (`Backend/app/api/staff/`)
| Method & path | Login needed | What |
|---|---|---|
| `POST /api/staff/login` `{ username, password }` | – | → `{ account }` + session cookie (HttpOnly, until browser closes). 10 failed tries per 15 min → `429` |
| `POST /api/staff/logout` | – | Clears the session cookie |
| `GET /api/staff/session` | – | `{ authenticated, account }` |
| `GET /api/staff/accounts` | ✓ | All staff accounts |
| `POST /api/staff/accounts` `{ username }` | ✓ | → `{ account, password }` (password only returned here) |
| `PATCH /api/staff/accounts/:id` `{ isActive }` | ✓ | Deactivate/reactivate (not yourself, not the last active account) |
| `POST /api/staff/accounts/:id/reset-password` | ✓ | → `{ account, password }` (not your own) |
| `GET /api/staff/renters` | ✓ | People who reserve gear |
| `PATCH /api/staff/renters/:bnumber` `{ isActive }` | ✓ | Deactivate/reactivate a renter |

Future staff-only endpoints should start with `const { account, denied } = await requireStaff(request); if (denied) return denied;` (from `Backend/lib/staffAuth.js`) and record `account.username` as `staff_id`.

## 2. Sign-In & Role Enforcement (`student` / `faculty` / `staff` / `oap`)

[`SignInGate.tsx`](./app/rentals/SignInGate.tsx) performs two layers of validation:
1. **Client-side format check**: Requires a 9-character Berea `B#` (`/^B\d{8}$/i`, e.g. `B01234567`), a `@berea.edu` email address, full name, and role selection.
2. **Backend role verification (`POST /api/rentals/auth`)**:
   - Calls `verifyUserSignIn()` in [`api.ts`](./app/rentals/api.ts#L22-L64).
   - **How Staff / OAP access is enforced by the Backend**:
     - Roles match `users.role` in the database: `student`, `faculty`, `staff`, `oap`.
       - `oap` (Outdoor Adventure Program staff) is the **only** role that can manage reservations and gear.
       - `faculty` and `staff` are college employees: they can reserve faculty-only gear and request delivery, but cannot manage anything.
     - The backend looks up `bNumber` (and `email`) in the MySQL `users` table.
     - If a user attempts to sign in with a role higher than their database record (e.g. `userType: "oap"`, `"staff"`, or `"faculty"` when the record is `"student"`), the backend should return **`403 Forbidden`** with `{ "error": "Your B# is not authorized for this role." }`.
     - If valid, the backend returns **`200 OK`** with the authoritative `UserInfo` record from the database, which the frontend uses to unlock or hide `StaffDashboard` and `LogisticsDashboard`.
   - *(Note: While `Backend/app/api/rentals/` routes are still being built, a network/404 response falls back to a local POC session so UI development isn't blocked.)*

## 3. Rentals Backend API Contract (`/api/rentals/*`)

All endpoints below are called by [`Frontend/app/rentals/api.ts`](./app/rentals/api.ts) and map directly to Next.js App Router route handlers under `Backend/app/api/rentals/`.

### 3.1 `POST /api/rentals/auth`
Verify user identity and role against the `User` table (or create a `student` record if new).
- **Backend Route File**: `Backend/app/api/rentals/auth/route.js`
- **Request Body**:
  ```json
  {
    "bNumber": "B01234567",
    "email": "razotet@berea.edu",
    "fullName": "Tristan Razote",
    "userType": "oap"
  }
  ```
- **Response (`200 OK`)**:
  ```json
  {
    "userId": "U-01234567",
    "bNumber": "B01234567",
    "email": "razotet@berea.edu",
    "fullName": "Tristan Razote",
    "userType": "oap"
  }
  ```
- **Error Response (`401` / `403`)**:
  ```json
  {
    "error": "Your B# is not authorized for OAP Staff access."
  }
  ```

### 3.4 `PATCH /api/rentals/items/:id`
Update an item's logistics fields OR clear an item from the OAP Cleaning/Repair Hold Queue.
- **Backend Route File**: `Backend/app/api/rentals/items/[id]/route.js`
- **Request Body (Mark Cleaned / Ready)**:
  ```json
  {
    "condition": "Good",
    "needsCleaning": false,
    "maintenanceCount": 0,
    "staffId": "B01234567"
  }
  ```
  *(Or full `GearItem` fields when edited in the Item Logistics modal.)*
- **Response (`200 OK`)**: Returns the updated `GearItem` (or `{ "gearId": "G01" }`).

### 3.8 `PATCH /api/rentals/reservations/:id`
Used for 3 staff/user operations on an existing reservation:

1. **Status Change (`Approved`, `Denied`, `Checked Out`)**:
   - **Request Body**:
     ```json
     {
       "status": "Checked Out",
       "staffId": "B01234567",
       "checkoutDate": "2026-11-04",
       "historyEntry": {
         "timestamp": "2026-11-04 14:10",
         "staffId": "B01234567",
         "staffName": "Tristan Razote",
         "action": "Checked Out gear"
       }
     }
     ```
2. **Check-In / Return (`Returned` + Condition & Cleaning Flag)**:
   - **Request Body**:
     ```json
     {
       "status": "Returned",
       "returnCondition": "Good",
       "needsCleaning": true,
       "conditionNotes": "Good · Needs Cleaning — muddy rainfly",
       "checkinDate": "2026-11-15",
       "staffId": "B01234567",
       "historyEntry": {
         "timestamp": "2026-11-15 16:00",
         "staffId": "B01234567",
         "staffName": "Tristan Razote",
         "action": "Checked In (Good · Needs Cleaning)"
       }
     }
     ```
3. **Edit Notes (`notes` / `conditionNotes`)**:
   - **Request Body**:
     ```json
     {
       "notes": "Updated user notes",
       "conditionNotes": "Updated staff condition notes",
       "staffId": "B01234567",
       "historyEntry": {
         "timestamp": "2026-11-05 11:20",
         "staffId": "B01234567",
         "staffName": "Tristan Razote",
         "action": "Updated reservation / condition notes"
       }
     }
     ```
- **Response (`200 OK`)**: Returns the updated fields (matching the request body).
